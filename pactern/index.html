THE CHANGE THAT MATTERS

A passing build can still break the agreement.

An AI agent can make a failing test green by fixing the code. It can also change the expected result, remove the check, or relax the requirement. The new green build may describe a different agreement from the one you meant to keep. Developers need a stable point of comparison when they review the change.

01

Four units from a balance of three.

A quota service should reject that request. A missing guard computes the candidate result Ok(-1), which violates the nonnegative-balance requirement. If the acceptance rule lives only in editable tests or a prompt, an agent can make the failure disappear by editing the rule along with the implementation.

What should stay true A valid reservation succeeds; an invalid one returns the specified error; the balance never becomes negative.

Requirements that move with the patch

The design puts contracts and acceptance rules under an external trusted baseline. A direct text edit must face the same gate as a structured agent proposal.

Protocol design ↗

Access broader than the task

Declared effects make requested operations visible. A host is designed to issue scoped handles for particular resources or tenants; an effect declaration alone cannot grant access.

Language design ↗

A patch built on an old snapshot

Change requests carry a workspace revision and hashes for their targets. The candidate is meant to be checked in isolation, then committed only if the full input and policy still match.

Staging and commit rules ↗

Evidence that overstates what was checked

A proof, a runtime guard, an executed test, and a solver timeout mean different things. Pactern's protocol gives unknown and unsupported results their own status instead of treating them as success.

Diagnostic protocol ↗

These are design requirements for Pactern's toolchain, not features of the current CLI. Existing languages and tools can support similar practices; Pactern is exploring how to make them part of one change workflow.

ONE AGREEMENT, THREE QUESTIONS

The agreement belongs to you.

A pact connects the behavior you require, the authority a component receives, and the evidence used to accept a change.

01

Behavior

Write preconditions and postconditions next to the module's contract. A useful requirement gives both the implementation and a reviewer a concrete target.

02

Authority

Describe effects in source, then let trusted host configuration decide which scoped handles to provide. Candidate code cannot install its own permission baseline.

03

Evidence

Tests remain valuable. They are not universal proofs. Static results, runtime checks, tests, and unknowns stay separate so acceptance can account for each. You still decide whether the requirements are the right ones.

A SMALL, USEFUL CORE

A repair should preserve the requirement.

The contract and implementation are ordinary readable .ptn source. In the design, a compiler gives tools the same names, types, effects, and contract relationships that people see in the files.

The language specification defines checked I64 arithmetic, Option and Result, immutable values by default, and explicit local mutation.

module quota;

pub enum ReserveError {
    InvalidAmount,
    InsufficientQuota,
}

pub fn reserve(
    available: I64,
    amount: I64
) -> Result<I64, ReserveError> {
    if (amount <= 0) {
        return Result::Err(
            ReserveError::InvalidAmount
        );
    }
    if (amount > available) {
        return Result::Err(
            ReserveError::InsufficientQuota
        );
    }
    return Result::Ok(
        available - amount
    );
}

module quota;

pact reserve_safety for reserve {
    requires available >= 0;
    ensures match (result) {
        Result::Ok(remaining) =>
            amount > 0 &&
            amount <= available &&
            remaining ==
                available - amount &&
            remaining >= 0,
        Result::Err(
            ReserveError::InvalidAmount
        ) =>
            amount <= 0,
        Result::Err(
            ReserveError::InsufficientQuota
        ) =>
            amount > 0 &&
            amount > available,
    };
}

WHEN THE REQUIREMENT CHANGES

Deleting the pact is a specification change.

The protocol draft distinguishes an implementation repair from an edit to the agreement. Protected contracts, helpers, and required tests are tied to an external baseline; a specification change requires review and approval against the exact candidate diff. The request itself cannot approve the rule it changes.

CHANGE WORKFLOW · DESIGN

Give the agent context for the change.

A proposed repair needs a stable target, the surrounding meaning, and a reviewable account of what it changed.

01

Inspect the project

Semantic commands are designed to expose symbols, signatures, callers, effects, and linked contracts. An agent can ask where a behavior lives before guessing across a repository.

02

Propose a narrow edit

A change request names a symbol and the declaration hash it expects, or supplies a pact ID for a specification edit. The request describes an operation, not an arbitrary file write.

03

Check an isolated candidate

The design reparses and checks the complete candidate before it is shown. Review can include changed interfaces, effects, obligations, performed checks, and what remains unknown.

04

Commit against the same inputs

Workspace revisions include participating dirty and untracked files, dependencies, configuration, tools, and policy. If the snapshot has gone stale, the whole change is rejected instead of overwriting newer work.

WHY MAKE A LANGUAGE?

One meaning across the tools.

A compiler, interpreter, verifier, semantic editor, and runtime can disagree if each invents its own account of a program. Pactern defines a small shared language so those tools have one meaning to preserve.

Take integer overflow. Pactern specifies signed 64-bit I64 arithmetic that traps when the result cannot be represented, in every build mode. A verifier working with unbounded mathematical integers could approve an addition that generated code then wraps or handles differently. The implementation, interpreter, and prover are meant to share the same typed rules.

The same choice favors explicitness in everyday code: familiar functions, modules, braces, enums, Option and Result; immutable values by default; local mutation written explicitly. A small language is useful only if the rules stay small enough to specify, test, and explain.

WebAssembly is a deployment boundary in the plan, not a permission system by itself. The host must separately decide which scoped handles to provide and enforce memory, execution, and operation budgets. Likewise, proving arithmetic does not make a database update atomic or enforce tenant isolation; the transaction host has to do that work.

Could this be tooling for Rust or Go? Those ecosystems already have strong compilers and tools. Pactern puts the editor, acceptance model, and runtime around one contract so a repair is checked against the same semantics that code executes. The project will test that hypothesis against strong Rust and Go workflows under matched tasks and budgets. Comparative results are not available yet.

A FIRST BOUNDARY

Start with work you can describe.

The initial target is a bounded backend component called by an existing application, not a wholesale rewrite.

Quota and resource reservations

Specify which requests succeed, which errors they return, and how the remaining balance relates to the starting balance. A storage host still owns atomic updates and tenant isolation.

Business rules · account limits · capacity checks

Validation and transformations

Make accepted inputs, explicit error cases, and output invariants visible in one small component. Useful when an agent is changing the transformation and its contract needs to stay put.

Parsing results · normalization · data conversion

Bounded backend jobs

Give a task a narrow set of host-provided operations and planned runtime budgets. A job should have a clear input, output, and resource boundary before it runs.

Queue handlers · scheduled work · policy checks

First target: sandboxed backend components. The component host and application integration are planned.

BUILD THE SCAFFOLD

See what exists today.

Clone the repository and use the pinned Rust toolchain. These commands build and inspect the current CLI; they do not compile Pactern programs.

Prerequisites: Git and Rust via rustup. The repository pins Rust 1.98.1.

git clone \
  https://github.com/andrewarrow/pactern.git
cd pactern
cargo build --workspace \
  --locked
cargo test --workspace \
  --locked
cargo run -p pactern-cli \
  -- version --json
cargo run -p pactern-cli \
  -- --help

Optional local install:

cargo install --path \
  crates/pactern-cli \
  --locked
