01 / The thing that feels backwards

I have nothing against Roblox. It taught an entire generation that a game could also be a place, a toolbox, a social network, and a little economy. That is an enormous achievement. My problem is that the economics of a platform show up everywhere in the experience, especially when the customers are children and the people paying are their parents.

Virtual currency makes a game feel like a shop even when the child came for play. Discovery starts to reward the games that already have money behind them. More time spent can look like success, even when a parent is looking at the clock and wondering why the evening disappeared. Safety becomes a permanent repair job because the platform was designed first for scale and only later for the realities of children meeting strangers online.

The business model is not a detail around the game. It becomes part of the game.

The obvious response is to build a smaller, safer Roblox. I think that is too narrow. The better question is what would happen if we started with a different alignment. A parent pays for access to a service. A creator gets rewarded for making something people genuinely want to play. A child gets to play without a brightly colored cash register following them around.

02 / The value proposition

Cubacadabra is a user-generated gaming platform with a flat family subscription as its intended business model. No Robux-style currency. No advertisements aimed at children. No paid boost that quietly turns discovery into an auction. The exact price, payout formula, and scale economics still need to be proved. That is not a footnote. It is the central business question.

The idea is a shared pool of subscription revenue, with a clear and capped formula for creators. If a creator makes a game that families love, there should be a path for that work to earn real money without requiring the creator to become an expert in in-game purchases. A small creator who is invisible on a massive platform might be visible here because discovery is not supposed to be pay to win.

This also gives parents a much simpler thing to understand. You are not loading money into a child account and hoping the next click is harmless. You are paying for a place where your child can play and make things. That is a normal software relationship. It has a beginning, an end, and a receipt that does not require a spreadsheet to decode.

Parents should be customers, not just the payment method.

That sounds almost boring, which is part of the appeal. Boring can be a feature when the alternative is a financial system designed to make a nine year old feel one purchase away from being left behind.

03 / Creation is the core loop

The long-term promise is not a larger pile of games to scroll through. It is a shorter distance between playing a game and understanding how it was made. A game should feel less like a sealed amusement park ride and more like a small world you can inspect, remix, and eventually build yourself.

Today, a Cubacadabra game is a portable package: a manifest, assets, and Luau rules. The shared engine reads the package and provides generic capabilities such as movement, collision, interaction zones, effects, audio, UI, and multiplayer state. The game owns the meaning. Rust does not know what a spell, a relay gate, or a schoolyard is. It knows how to run a world and hand the game the pieces it needs.

That separation matters. It means a creator can make Spellbound Schoolyard, where players learn Spark, Splash, and Sprout before celebrating in a Wand Circle. Another creator can make Signal Run, a cooperative race through signal gates. Both use the same runtime. Neither requires the engine to learn the theme. The platform gets more capable without turning every new idea into a special case.

For a child, this can be as simple as discovering that the world has rules and those rules can be changed. For a parent, it can look like play that leaves a trail toward making, storytelling, logic, collaboration, and maybe a first line of code. For a creator, it is the beginning of a real medium rather than another storefront with a level editor attached.

Every game should be an invitation to make the next game.
04 / One engine, several doors

The technical project is further along than the product story, which is a useful way to be honest about where this is. There is a platform-neutral Rust runtime shared by Studio, iOS, Android, and the browser. Native clients use the same engine through a C boundary. The browser uses WebAssembly. The renderer is built with wgpu. The game lifecycle runs through sandboxed Luau on both native and web targets.

That sounds like an implementation detail until you have watched a promising game become trapped in one client. A portable package changes the leverage. Build the game once, then load it in the browser, in an iOS app, in an Android app, or in the desktop Studio host. The shell changes for the device. The world and its rules do not have to be rewritten every time.

Studio is intentionally modest right now. It can open a raw project or a built package, show the live renderer, load assets, and connect to the multiplayer Worker. Its World, Assets, Materials, and Test layouts are an early workbench, not a finished editor. That is enough to make the direction tangible. The future editor should help a person move from an idea to a playable place without first becoming a full-time tools engineer.

The multiplayer service is a Cloudflare Worker with a Durable Object for each world. The WebSocket carries presence and movement. The game rules remain game-owned. Shared state is passed as opaque JSON with sequences and compare-and-set retries, so two players can act at once without one silently erasing the other. The jargon is not the point. The point is that the platform is being built as a set of reusable primitives, not as one enormous game with a few configurable colors.

05 / Trust is a product feature

A platform for children cannot treat safety as a paragraph on a terms-of-service page. It has to be part of the architecture and part of the business model. Cubacadabra is still early, but the direction is clear: parent controls should be understandable, reports should be actionable, and the system should preserve enough evidence to know what happened.

The current backend already has the beginnings of that shape. Players can block and report through normal authenticated requests. Reports are stored privately in D1. World sockets load a player's block list and filter subsequent presence and movement. That is useful infrastructure. It is not a solved safety program, and I do not want to pretend that a few endpoints solve the hardest problem on the internet.

I am especially wary of the idea that the answer is to turn random users into vigilantes. People want to help, but asking them to impersonate children, bait dangerous adults, continue harmful conversations, or carry screenshots into a moderation queue creates its own legal and human problems. A better direction is structured safeguarding: trained community roles, strict no-engage rules, authenticated in-platform records, rapid escalation, and independent review. If there is ever a decoy account program, it should be operated by trained staff under written protocols with counsel and appropriate authorities.

The incentive matters too. I do not want a bounty hunt for predators, because paying for shocking outcomes can create bad incentives. I would rather fund moderation and safeguarding work based on accuracy, quality, and reliability, with transparent reporting about what the system can and cannot do. A nonprofit structure may eventually make sense. So may a public safety commitment that survives changes in ownership. Those are serious questions for lawyers, operators, and parents to help answer from day one.

Safety is a community function with accountability, not a bounty hunt.
06 / Why open source

Open source is not a magic spell. It does not automatically make a platform safe, fair, or popular. It does make certain promises possible. The runtime can be inspected. The game package format can be documented. A creator can understand what they are shipping instead of handing a finished world to a black box and hoping the rules stay favorable.

The repositories are separate on purpose. Game projects contain manifests, assets, and Luau source. The Rust repository contains the shared engine and its native and WebAssembly adapters. The web client owns the browser shell. iOS and Android own their platform services. Studio owns the desktop host. Tools builds a game into a portable package. This is less glamorous than saying everything is one seamless metaverse, but it gives the pieces names and boundaries. Boundaries are where ownership starts.

Creators should eventually have choices about what they open. Some may want a closed server implementation, some may want source visible, and some may want a permissive remix license. The principle is not that every game must expose every secret. The principle is that openness should be a first-class option, with real files, clear licenses, proper credit, and a way to fork the work if the creator wants that.

This matters to investors too. A closed platform can be defensible because nobody else can leave. An open platform has to be defensible because people want to stay. The moat, if there is one, is the combination of a trusted family product, a growing library of good games, creator tools that reduce the cost of making them, and a payment system that attracts talent without extracting from children. That is a harder moat to build. It is also a healthier one.

The goal is not to trap people in the platform. It is to give them a reason to return.
07 / The bet and the unfinished parts

The business flywheel is straightforward to describe and difficult to earn. Parents pay a subscription. That money supports creators and the service around them. Creators make better games because they can be discovered and paid without building a casino. More families join because there is something worth playing and because the rules make sense. More families make the pool and the audience more meaningful for creators.

The hard questions are not hidden. How much of a monthly fee remains after app stores, infrastructure, support, moderation, insurance, and taxes? What is a meaningful payout for a creator? How do you acquire families when Roblox, Fortnite, and Minecraft already occupy the conversation? How do you make the first ten minutes delightful before the network is full? Can a smaller community be sustainable before it becomes large? These are the questions a serious investor should ask, and the answers need numbers, not optimism.

The current answer is to build the smallest credible system and keep testing it. Developer Preview 0.3 has three example packages, a shared engine, a browser client, native clients, a desktop host, a multiplayer Worker, build tools, and a conformance game that exercises the game-facing SDK. It is not yet the polished product I want a family to subscribe to. It is a working argument that the architecture can support one.

That is why I started Cubacadabra. Not because I think every existing game platform is evil, and not because open source solves parenting. I started it because the default relationship between a child, a game, and a business feels more permanent than it should. There is room to try a different relationship, one where play is valuable before it is monetized and where the people paying for the service are allowed to know what they are buying.

We should optimize for creating value for children, not extracting value from them.

If you are a parent, I want to know what would make you trust this. If you are a creator, I want to know what would make the tools worth learning. If you are an engineer, there is a Rust engine, a Luau package format, a web client, a backend, and plenty of unglamorous work waiting. If you are an investor, the opportunity is not just another game catalog. It is a chance to help prove that a family software business can align its revenue with the health of the people using it.

The magic is not in the name. The magic would be getting all of those incentives to point in the same direction.
